## Task brief · secrets

```
Problem       The workspace's development-time secrets sit in untracked files on one
              laptop (the spike gateway's keys, the Azure Foundry key), and the
              integration tiers read whatever the caller exported. ai-hosting's later
              tasks need secrets on the hosts (the gateway's Azure key, issued consumer
              keys), so a convention must exist before hosts and gateway build on it,
              and future spikes must stop copying ad hoc ones.
Behaviors     1. One private store repository holds every development-time secret,
                 encrypted by fnox's age provider, in a global file and one file per
                 consuming repository; its recipients name each enrolled device
                 (laptop, gb10-2) and an offline backup. No private key or plaintext
                 value is ever committed, and the store's check refuses both.
              2. A consumer imports its own file and the global file; a value in its
                 file overrides the global one, and a gitignored local file overrides
                 both for one machine.
              3. Each enrolled device's own age identity decrypts every value.
              4. An existing device enrolls a new one: its public key joins the
                 recipients, every value is re-encrypted in one commit, and the new
                 device reads every value after a pull. Proven by enrolling gb10-2.
              5. The passphrase-protected backup identity alone, on a clean config,
                 decrypts every value (restore).
              6. In ai-hosting, the Azure Foundry key and account resolve from the store
                 and reach only a task that lists them; check and currency run
                 unchanged without the store. fnox (and age, for key generation) are
                 pinned, and currency reports them.
              7. go-ai's integration task and docinfer's test:integration take the
                 store's gateway key as every role's AI_<ROLE>_TOKEN, redacted in
                 output, and pass against the spike gateway. In a clone without the
                 store they run exactly as today (pass-through, skip when unset), and a
                 caller can still run them deliberately with their own credentials.
              8. Published development credentials (Azurite's well-known key, MinIO
                 admin/secret, Postgres "app", go-web-service's secrets.example.json)
                 stay committed, named as not-secrets.
              9. Architecture's "Development-time secrets" principle states the
                 convention: the store and its hierarchy, a key per device, the
                 passphrase-protected backup, per-task grants, add-device, rotate,
                 restore, and what isn't a secret; the architecture check passes.
             10. Repository pointers: each consumer's STANDARDS.md points at the
                 principle, and the coordinator's Experiments line resolves to it.
Test seams    fnox against the store (check, reencrypt, restore on a clean config);
              mise's per-task grant in each consumer (secrets listing, a granted run,
              a run with the store absent)
Slices        1 store: the private repository, pins, recipients (laptop, backup),
                the Azure key and account, the spike's go-ai key, its check; demo
                restore with the backup alone
              2 add-device: gb10-2 enrolls by the runbook; demo a read after pull
              3 ai-hosting: the grant and its import; demo listing; check and
                currency pass without the store
              4 go-ai: the integration task on the store, store-absent and
                caller-credential paths; demo a redacted pass against the spike gateway
              5 docinfer: the same for test:integration
              6 architecture: the principle and its index; consumers' STANDARDS.md
                pointers
Out of scope  the gateway's consumer key set and the key group (gateway); HF tokens
              (each host's cache); enrolling gb10-1 and the Framework; go-ai's
              hand-run Foundry recorder; CI secrets; archived spikes; a hosting
              secrets group; hardware/plugin age identities
Door          two-way for every file; one-way in part: a value committed to the
              store stays readable in its history by every identity it was
              encrypted to, and only rotation revokes it. Creating the private
              repository is undoable. No release.
```

## Decisions

- plan: The repository's name is `ai-hosting`, settled now; the design task no longer settles it.
- plan: Kind `code`.
- plan: Check: `mise run check` — shellcheck on tracked scripts, relative Markdown links resolve.
- plan: Currency: `mise run currency` over mise tool and CI action pins; hosts and gateway add image pins.
- plan: GitHub Actions CI as docinfer; merge waits on checks; `[remote] ci` wait.
- plan: No release gate at init.
- plan: `order`: peer of claude-plugins in the lowest layer; acceptance's use of the architecture's components is not a dependency. Outside `exclusive`.
- plan: design's brief is written into the record now.
- plan: The script suite's root command is `hosting`, with engines' `<group> <verb>` dispatch.
- plan: Read-only operator commands (row status with the stranded-container check, served model, `/metrics`, GPU memory) are built in v1.ai.hosting; preset-install and service-restart drop; spike-host-admin takes ai-hosting's commands as its baseline.
- plan: Commands are host-class transparent. Only commands that differ by host class detect it. One shared detection function probes the hardware once per call (`HOSTING_CLASS` overrides), and each command dispatches to its own private per-class function.
- plan: An install step symlinks the commands into `~/.local/bin`; uninstall removes exactly its links.
- plan: ai-hosting is the only hosting repository on the workstations. A new task, `cleanup`, after gateway, removes every spike clone, gb10-2's `~/gateway`, spike-ai-pipeline's router, outpost links, and stale images and units; hosts removes only what it replaces.
- plan: The gateway's six open points are listed by design and settled at the gateway task's plan.
- plan: design confirms multilingual-e5-large's scope and price on Foundry managed compute.
- plan: The `architecture` overlap with v1.ai.processing and harness.optimization stays, as the intake accepted (PR #174 decision 2).
- design: Every finding of the three evaluations is settled in the capability notes, `context/engines.md`, `context/hosting-suite.md`, `context/host-classes.md`, `context/gateway.md`, `context/secrets.md`, and `context/cleanup.md`; the evaluations are removed.
- design: The `hosting` suite's groups are `engine`, `model`, `profile`, `gateway`, and `key`; the mise tasks `install` and `uninstall` link and unlink it.
- design: Each host class's profile is the one home of every row it serves: TOML, read by the suite's shell commands, with no Go.
- design: The gateway's config is the one home of the map from each alias to its tailnet host.
- design: Development-time secrets use fnox's age provider and a private `secrets` store repository; each consumer imports the store's global file and its own repository's file, and the repository's file overrides the global one.
- design: Published development credentials (Azurite's well-known key, MinIO's admin/secret, Postgres's "app", go-web-service's `secrets.example.json`) are not secrets and stay committed.
- design: A comment that explains links to the document or principle that governs it instead of restating its reasoning.
- design: The gateway's compose files are layered as go-web-service's: a root `compose.yml` includes one `compose/<service>.yml` per service, each built from its own `compose/<service>/Dockerfile`.
- design: A task `secrets` runs right after design; `comment-kinds` drops, superseded by design.
- design: `secrets` shares go-ai and docinfer with v1.ai.inference until it ships.
- design: The architect runs `secrets` alone, once harness.adoption completes.
- secrets plan: Values use fnox's age provider, not SOPS files: fnox reads no SOPS file, and mise's SOPS path drops the per-task grant.
- secrets plan: The store is one private `secrets` repository; consumers import its global file and their own, the repository's file overriding.
- secrets plan: The store carries the Azure Foundry key and account and the spike gateway's `go-ai` key; the gateway task replaces that key with issued ones.
- secrets plan: The existing integration tasks take the grant, and still run as today without the store or with a caller's own credentials.
- secrets plan: The task enrolls the laptop, gb10-2, and a passphrase-protected offline backup; age is pinned for key generation only.
- secrets plan: The convention's page is an architecture-level principle, "Development-time secrets".
