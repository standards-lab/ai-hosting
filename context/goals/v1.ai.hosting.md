## Task brief · migrate

**Problem**

gb10-1, gb10-2, and the Framework still serve their rows from spike-model-engines clones. The containers are unlabeled, and they use the spike's ports. gb10-2 also still runs the spike gateway. Each host keeps leftovers from earlier spikes: clones, run logs, images, helper scripts, and firewall rules. The `hosting` suite is built, but no host runs it.

This task does three things:
- It moves every host onto one ai-hosting clone, with each row on its profile port: agent 8000, vision 8001, audio 8002, embedding 8003.
- It retires the spike gateway. Callers use the rows directly until the `gateway` task.
- It leaves each host in its final state, with nothing from the spikes.

Today a spike container on a row's port leaves a labeled, never-started row that a rerun records as installed. The suite has to refuse before it touches anything.

**Behaviors**
1. `hosting engine install` refuses an alias, exits non-zero, and names the container and the command that removes it, when:
   - a container without the row label, running or stopped, has the row's container name; or
   - a running container without the row label publishes the row's port.

   It refuses before it pulls a model, fetches an image, starts a container, or writes the install record.
2. `hosting engine update` applies the same refusals to every alias it acts on, before any pull.
3. The row's own labeled container never triggers the refusal. Install still reports it as already installed, and update still replaces it or leaves it as today.
4. Each host has ai-hosting cloned as `ai-hosting` in the serving account's home. Its pinned tools are installed, mise trusts it, and `hosting` is linked into it. With no arguments, `hosting` lists every command.
   - The clone is on the `migrate` branch during BUILD.
   - gb10-2's clone under `architecture` is gone, and so is that directory.
5. Every root step in each host's class runbook passes its read-only check. You ran only the steps that failed.
   - The Framework's ufw allows routed tailnet traffic to 8002 and 8003, and no longer allows it to 8000, 8001, or 8080.
   - The Framework's sudoers directory holds no rule from the spikes.
6. Each host serves its rows from labeled containers on its tailnet address:
   - gb10-1: `agent` on 8000;
   - gb10-2: `vision` on 8001;
   - the Framework: `embedding` on 8003, installed first, then `audio` on 8002 from the image ai-hosting builds.

   Each host's install record lists exactly its aliases. From the laptop, each row's `/v1/models` answers with its alias.
7. On every host:
   - `hosting engine status` exits 0;
   - `hosting engine update` with no alias reports nothing changed for every alias;
   - `hosting model prune` lists nothing to remove.
8. No host runs a container from the spike. The Framework's three spike audio images are gone. The shared vLLM base images stay.
9. These directories and files are gone:
   - every host: `repos` and `prestage`;
   - the GB10s: `scripts`;
   - the Framework: `spike-harness-driver`, the three `clutch-*` directories, `personal-agents`, `framework-align-b11529.sh`, and `rocm-pull.log`.
10. gb10-2 has no spike gateway:
    - the `gateway` compose project has no containers, volumes, or network;
    - its four built images and the agentgateway image are gone;
    - the `gateway` and `agentgateway` directories are gone;
    - nothing listens on gb10-2's tailnet ports 3000 or 4317.
11. go-ai's vLLM fixture record scripts name vision at gb10-2:8001 and audio at framework:8002. Agent stays at gb10-1:8000.
12. After the merge, each host's clone is on main, and behaviors 6 and 7 hold again.

**Test seams**
- **Behaviors 1–3:** the `hosting` command, run through the shell-test harness with a Docker stub and a fake system root.
  - The stub presents an unlabeled holder of the row's name or port.
  - The tests assert the exit status, the message, an unchanged install record, and a call log with no pull, build, or run.
  - Each refusal is tested for both install and update, along with the case where the labeled container is not refused.
- **Behaviors 4–10 and 12:** read-only ssh checks from the laptop, listed in each slice's demo. Their output goes into the session brief's Verify section.
- **Behavior 11:** go-ai's check, plus a read of the three scripts.

   - Clone at `migrate`, and run suite commands through `mise exec`.
   - You add the ufw rule for 8003, remove the rules for 8000, 8001, and 8080, and read the sudoers directory.
   - Remove `vllm-embed`, then install `embedding`. Remove `vllm-audio`, then install `audio`.

**Out of scope**

- The `gateway` task's stack, keys, and routes. No temporary gateway is built and no route is repointed.
- The `embedding` task's model replacement, and any change to a profile.
- Enrolling gb10-1 or the Framework in fnox.
- The Framework's TTM step, and any reboot.
- The laptop's `experiments` clones. Archiving the spike remotes is the goal sync's job.
- In go-ai: the fixture READMEs, `AI_GATEWAY_TOKEN`, and re-recording fixtures. docinfer is not touched.
- Anything not from a spike: the vLLM compile cache, the hf token, the Docker drop-ins, the `drop-caches` sudoers rule, `Work/tries`.
- The notes, which BUILD's editor pass updates.

**Door**

The code change and the go-ai edit are two-way. The host removals are one-way:
- The spike gateway's volumes go with it: the Postgres request log, Tempo traces, and Grafana. They hold only the spike's benchmark traffic.
- These local-only files are lost, and nothing committed cites any of them:
  - the Framework's spike `.state` (96K);
  - nine ignored plan files in `personal-agents`;
  - the clutch run outputs;
  - the `prestage` logs.
- Clones and images can be recovered from their remotes or rebuilt.

## Decisions

- plan: The `architecture` overlap with v1.ai.processing and harness.optimization stays, as the intake accepted (PR #174 decision 2).
- secrets plan: The gateway task replaces the spike gateway's key, `AI_GATEWAY_TOKEN` in go-ai's and
  docinfer's `fnox.toml`, with keys it issues.
- secrets: Enrolled the laptop and gb10-2, gb10-2 in ai-hosting alone; enrolling gb10-1 and the
  Framework is left to a later task.
- hosts plan: Moving the hosts onto ai-hosting is its own task, `migrate`, after hosts; hosts
  changes nothing on a host.
- hosts plan: A host records its installed aliases under `$XDG_STATE_HOME/hosting`; update and
  uninstall with no alias read it.
- hosts plan: No row carries a sampling override in v1.
- hosts plan: Any change to the Framework's LUKS unlock at the console goes to the backlog.
- hosts plan: Shell tests are plain-bash scripts run by the check; bats-core rejected: it adds a
  tool, and claude-plugins' plain-bash tests are the workspace precedent.
- hosts: Each alias has one port across the classes: agent 8000, vision 8001, audio 8002,
  embedding 8003.

- migrate plan: ai-hosting is cloned as `~/ai-hosting` on every host. `~/repos` and gb10-2's `~/architecture` are removed.
- migrate plan: the spike gateway is retired in migrate. Callers use the rows directly until the `gateway` task, whose handover starts from an empty gb10-2. Rejected: folding in `gateway`, which has six open points and depends on `embedding`; and a temporary gateway.
- migrate plan: `cleanup` is folded into migrate. It stays in `order` and Tasks, and is checked off at migrate's SHIP.
- migrate plan: the laptop's `~/experiments` clones stay. "Workstation" means the three hosts.
- migrate plan: go-ai joins migrate's repositories, only for the record scripts' ports.
