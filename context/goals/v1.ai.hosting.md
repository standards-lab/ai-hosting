## Task brief · hosts

**Problem**

Today every host runs its vLLM rows from a clone of spike-model-engines, from a free-form rows
file beside scripts that still carry llama.cpp, a native vLLM path, and no row label. ai-hosting
doesn't yet specify the rows or a command that runs them. The `migrate` task needs a specified,
checked `hosting` suite before it can move a host onto ai-hosting, and every later task needs it.

**Behaviors**
1. `mise run install` links one command, `hosting`, into `~/.local/bin`; `mise run uninstall`
   removes the link only when it points into this clone.
2. `hosting` with no arguments lists every `<group> <verb>` with a one-line summary. An unknown
   command or a usage error prints to stderr and exits 2.
3. Class detection: a positive probe sets `gb10` or `strix-halo`, and a host matching neither is
   refused. `HOSTING_CLASS` overrides the probe and is checked against the same closed list. Only
   commands that differ by class detect it, once per call; uninstall never detects.
4. `profile validate` checks every committed class profile, and the check runs it. It reports
   every error at once, each by key path, and refuses: unknown keys; duplicate aliases, ports, or
   containers; a fraction over 1; a queue limit that isn't twice the cap; a context over the
   card's; a missing reason; flags the typed fields own; a free flag without a reason; a value
   with whitespace or shell syntax; any address or MagicDNS name; an origin or base origin of
   China without `origin_reason`, and `origin_reason` on any other origin. Each refusal has a
   fixture producing its error.
5. Each class profile holds its standing rows (gb10: agent, vision; strix-halo: audio,
   embedding), each with its cited provenance. The vision row has no sampling override, and its
   provenance records that its generation config matches the card's.
6. `profile render <alias>` prints the image and the full container and `vllm serve` settings a
   row runs; install and update use the same function. For each standing row, the rendered
   arguments equal those its spike container runs now, apart from the row label, the container
   name, the bind address, and the port, which follows the port map (agent 8000, vision 8001,
   audio 8002, embedding 8003).
7. `profile set <alias> <field>=<value>` edits the committed profile in place, validating first
   and writing nothing when validation fails.
8. `engine install <alias>...` validates the profile, then refuses before touching Docker on: an
   unknown alias; fractions summing over 1 across the host's recorded aliases plus the new ones;
   `net.ipv4.ip_nonlocal_bind` not 1 (pointing at the runbook step); on gb10, a CDI spec naming
   a missing driver library (printing the regenerate command). It runs `model pull`, builds the
   row's image if it names one, starts a labeled container bound to the tailnet address, and
   appends the alias to the host's record under `$XDG_STATE_HOME/hosting`.
9. `engine update [<alias>]` pulls or builds first, replaces a row whose image ID or command
   differs from its running container, installs an absent row, and removes the superseded build.
   With nothing changed it does nothing. With no alias it acts on the record.
10. `engine uninstall [<alias>]` removes the labeled container, then its image if no other
    container uses it, and drops the alias from the record; with no alias it acts on the record.
    No command uses sudo.
11. `engine status` shows each labeled row's state and health, and flags a running container with
    no published port or no network, printing `docker network connect bridge <container>`.
12. Read-only, changing nothing: `engine models` prints each row's served model from its
    `/v1/models`; `engine metrics <alias>` summarizes its `/metrics`; `engine memory` prints GPU
    memory per row — gb10 from nvidia-smi's per-process figure joined by container PID, with
    `MemAvailable`; strix-halo from `amdgpu_top -p`, with GTT.
13. `model pull <repo>` downloads with hf, using the token when present, failing clearly only on a
    gated repository. `model list` shows the store's models, sizes, and the rows using them.
    `model prune` lists unused models and incomplete downloads, deleting them only with `--yes`.
14. Currency reports the vLLM release pin, the audio image's base digest and its three Python
    pins, and the hf and uv pins. The audio image is named under ai-hosting and sets
    `MIOPEN_FIND_MODE=FAST`.
15. Each class has a runbook beside its profile, covering the root steps (nonlocal bind and the
    store; gb10's CDI regeneration; strix-halo's GTT limit and ufw rules), the suite's install,
    and every row's commands. The strix-halo runbook documents the LUKS passphrase at the console.

**Test seams**
- The `hosting` command, run by plain-bash test scripts from the check, with stub commands on
  PATH for `docker`, `nvidia-smi`, `amdgpu_top`, `tailscale`, `hf`, and `curl`, and a fake system
  tree for the probes and sysctl. Tests assert the commands issued and the output printed.
- Profile fixtures, each paired with its error; rendered golden commands for the four rows.

**Slices**
1. Upgrade ai-hosting to marathon 0.23.0 and move the CI wait into `[remote] checks`; done when
   currency exits 0 and the check passes.
2. The suite: dispatcher, install and uninstall, class detection, and the test harness in the
   check. Behaviors 1–3.
3. The profile schema document, the two class profiles, and `profile validate` with fixtures.
   Behaviors 4–5.
4. `profile render` and `profile set`, with the golden commands. Behaviors 6–7.
5. `model pull` with the hf and uv pins, then `engine install`, `update`, and `uninstall` with
   the preflight, install record, audio image, and currency additions. Behaviors 8–10, 14.
6. The read-only verbs: `engine status` with the stranded-container check, `models`, `metrics`,
   `memory`. Behaviors 11–12.
7. `model list` and `model prune`. Behavior 13.
8. The runbooks, and a read-only ssh comparison of each standing row's render against its spike
   container's arguments. Behavior 15 and behavior 6's proof.

**Out of scope**
- `migrate`'s work: cloning ai-hosting on each host, linking the suite there, replacing the spike
  containers with `engine install`, removing only what that replaces.
- cleanup's work: spike clones, spike-named and llama.cpp images, native vLLM, units, sudoers,
  outpost links, gb10-2's `~/gateway`, spike-ai-pipeline's router.
- The `gateway` and `key` groups, the embedding swap, the upgrades convention, and enrolling
  gb10-1 and the Framework for secrets.

**Door**

Two-way. Every change is in ai-hosting and nothing on a host changes; the only host contact is
slice 8's read-only comparison.

- plan: Kind `code`.
- plan: Check: `mise run check` — shellcheck on tracked scripts, relative Markdown links resolve.
- plan: Currency: `mise run currency` over mise tool and CI action pins; hosts and gateway add image pins.
- plan: GitHub Actions CI as docinfer; merge waits on checks; `[remote] ci` wait.
- plan: No release gate at init.
- plan: `order`: peer of claude-plugins in the lowest layer; acceptance's use of the architecture's components is not a dependency. Outside `exclusive`.
- plan: design's brief is written into the record now.
- plan: The script suite's root command is `hosting`, with engines' `<group> <verb>` dispatch.
- plan: Read-only operator commands (row status with the stranded-container check, served model, `/metrics`, GPU memory) are built in v1.ai.hosting; preset-install and service-restart drop; spike-host-admin takes ai-hosting's commands as its baseline.
- plan: Commands are host-class transparent. Only commands that differ by host class detect it. One shared detection function probes the hardware once per call (`HOSTING_CLASS` overrides), and each command dispatches to its own private per-class function.
- plan: An install step symlinks the commands into `~/.local/bin`; uninstall removes exactly its links.
- plan: ai-hosting is the only hosting repository on the workstations. A new task, `cleanup`, after gateway, removes every spike clone, gb10-2's `~/gateway`, spike-ai-pipeline's router, outpost links, and stale images and units; hosts removes only what it replaces.
- plan: The gateway's six open points are listed by design and settled at the gateway task's plan.
- plan: design confirms multilingual-e5-large's scope and price on Foundry managed compute.
- plan: The `architecture` overlap with v1.ai.processing and harness.optimization stays, as the intake accepted (PR #174 decision 2).
- design: Every finding of the three evaluations is settled in the capability notes, `context/engines.md`, `context/hosting-suite.md`, `context/host-classes.md`, `context/gateway.md`, `context/secrets.md`, and `context/cleanup.md`; the evaluations are removed.
- design: The `hosting` suite's groups are `engine`, `model`, `profile`, `gateway`, and `key`; the mise tasks `install` and `uninstall` link and unlink it.
- design: Each host class's profile is the one home of every row it serves: TOML, read by the suite's shell commands, with no Go.
- design: The gateway's config is the one home of the map from each alias to its tailnet host.
- design: A comment that explains links to the document or principle that governs it instead of restating its reasoning.
- design: The gateway's compose files are layered as go-web-service's: a root `compose.yml` includes one `compose/<service>.yml` per service, each built from its own `compose/<service>/Dockerfile`.
- secrets plan: Values use fnox's age provider, not SOPS files: fnox reads no SOPS file, and mise's SOPS path drops the per-task grant.
- secrets plan: The gateway task replaces the spike gateway's key, `AI_GATEWAY_TOKEN` in go-ai's and
  docinfer's `fnox.toml`, with keys it issues.
- secrets: Enrolled the laptop and gb10-2, gb10-2 in ai-hosting alone; enrolling gb10-1 and the
  Framework is left to a later task.
- hosts plan: Moving the hosts onto ai-hosting is its own task, `migrate`, after hosts; hosts
  changes nothing on a host.
- hosts plan: hosts touches ai-hosting alone.
- hosts plan: Profiles are read and written with mikefarah yq; committed profiles follow its
  in-place output format.
- hosts plan: Each class directory holds one `profile.toml` and one `runbook.md`.
- hosts plan: A host records its installed aliases under `$XDG_STATE_HOME/hosting`; update and
  uninstall with no alias read it.
- hosts plan: The fractions-sum-to-1 rule is checked at `engine install` against the record plus
  the new aliases; the validator checks only each fraction ≤ 1.
- hosts plan: The restricted-origin list is China alone (ai-strategy, "Constraint: model origin").
- hosts plan: No row carries a sampling override in v1.
- hosts plan: On gb10, GPU memory is nvidia-smi's per-process `used_memory`, joined by container
  PID, with `MemAvailable`.
- hosts plan: `engine uninstall` also removes the row's image when no other container uses it.
- hosts plan: The read-only verbs are `engine status`, `models`, `metrics`, and `memory`.
- hosts plan: The Framework's runbook documents the LUKS passphrase at the console; any change
  goes to the backlog.
- hosts plan: Shell tests are plain-bash scripts run by the check; bats-core rejected: it adds a
  tool, and claude-plugins' plain-bash tests are the workspace precedent.
- hosts: Each alias has one port across the classes: agent 8000, vision 8001, audio 8002,
  embedding 8003.
- hosts: `model prune` keeps only the models the install record's rows serve; a host holds only
  what its rows serve.
